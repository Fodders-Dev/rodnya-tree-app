# «Спросить историю» — сценарий реализации (13.09.2026)

> Статус: **MVP-1 реализован и в проде (13.09.2026)** — бриф и контракт в
> [STORY-REQUEST-MVP1-BRIEF.md](STORY-REQUEST-MVP1-BRIEF.md); MVP-2/3 — §5. Продуктовый дизайн уже
> есть в [PHASE-D-MEMORY-HISTORY-PROPOSAL.md](PHASE-D-MEMORY-HISTORY-PROPOSAL.md)
> §3.3 (Memory prompts) и §3.4 (Voice input) — этот документ не изобретает
> фичу заново, а раскладывает её на существующие кирпичи и три поставки.
> Лейтмотив: «поговори, пока есть возможность» — ответ голосом бабушки
> должен лечь на её страницу навсегда, а просьба должна доходить и до
> родных без приложения.

## 0. Что есть сегодня и в чём пробел

В коде живёт заглушка: на странице родственника кнопка «Спросить историю»
открывает лист с 8 вопросами (`lib/models/family_story_question.dart`,
`lib/widgets/family_story_questions_sheet.dart`) и либо отдаёт текст вопроса
в системный «Поделиться», либо открывает редактор статьи самому инициатору
(`relative_details_screen_sections.dart:661`). Серверной сущности «просьба»
нет: адресат не получает уведомления, инициатор не узнаёт об ответе, родной
без приложения ничего не может сделать по ссылке.

Кирпичи, которые переиспользуются без изменений:

| кирпич | где | роль в фиче |
|---|---|---|
| Статья персоны с блоками, блок `audio {url, durationSec, transcript}` | `backend/src/routes/profile-article-routes.js`, `lib/widgets/article_audio_block.dart` | **ответ хранится здесь**, навсегда, с правами `requireGraphPersonEdit` |
| Запись голоса до 15 мин | `lib/widgets/audio_record_sheet.dart` (`ChatRecordingController`) | экран ответа голосом |
| Видео-рекордер | `lib/widgets/kruzhok_recorder_screen.dart` | ответ видео (третий режим вызова) |
| Бинарная загрузка медиа | `PUT /v1/media/object` | загрузка ответа |
| Паттерн «просьба → ответ» | `backend/src/routes/kinship-checks-routes.js` (pending → accepted/rejected/expired/revoked, 5 типов уведомлений) | шаблон для `StoryRequest` 1:1 |
| Диспетчер уведомлений и пуши | `createAndDispatchNotification` (`app.js:2765`) → `pushGateway` | 4 новых типа |
| Capability-интерфейсы | `lib/backend/interfaces/kinship_check_capable_family_tree_service.dart` | новый интерфейс, старые бэкенды просто прячут кнопку |
| Приглашение по токену для гостя | `backend/src/routes/semya-invitation-routes.js`, `semya_invitation_deep_link_service.dart` | образец токен-флоу, но целевой экран другой |
| Посты с `anchorPersonIds` | `backend/src/routes/post-routes.js` | тизер «Мама рассказала о бабушке» в ленте |

Чего нет: сущности запроса, экрана ответа «от первого лица», уведомлений,
публичной страницы ответа для гостя, привязки блока статьи к вопросу.

## 1. Сценарий

**Роли.** Инициатор — участник дерева. Адресат — родной, у которого есть
аккаунт (привязан к персоне) **или** нет (гость по ссылке). Герой — персона,
о которой спрашивают (может совпадать с адресатом: «расскажи о своём детстве»).

1. Инициатор на странице персоны нажимает «Спросить историю», выбирает
   вопрос из банка или пишет свой, выбирает адресата: «спросить у самой
   бабушки» (если у персоны есть пользователь) или «спросить у…» (любой
   участник дерева) или «отправить ссылкой» (гость).
2. Адресат-пользователь получает пуш «Артём хочет узнать: “Как познакомились
   бабушка и дедушка?”». Тап открывает экран ответа: вопрос крупно, одна
   большая кнопка микрофона, ниже «Написать текстом», «Прислать фото»,
   «Пропустить пока» (§3.3.4 Phase D, запись стартует сразу по тапу).
3. Ответ сохраняется блоком в статью героя (аудио/видео с необязательной
   расшифровкой или параграф), запрос переходит в `answered`, инициатор
   получает пуш «Бабушка Лида ответила». На странице героя ответ виден в
   разделе «Истории» с подписью «На вопрос Артёма, 13 сентября».
4. Гость по ссылке `rodnya-tree.ru/story/{token}` видит ту же страницу
   ответа в вебе без входа: вопрос, кто спрашивает, кнопка микрофона,
   галочка согласия на хранение записи в семейном архиве. После сохранения —
   «Спасибо! Артём получит вашу историю» и мягкое приглашение установить
   приложение (существующий invite-флоу семьи). Аккаунт для ответа не нужен.
5. Необязательно: инициатор одним тапом публикует в ленту тизер-пост с
   `anchorPersonIds=[герой]` («✨ Бабушка рассказала, как познакомилась с
   дедушкой») — сам ответ остаётся в статье, в пост идёт только ссылка.

## 2. Экраны (MVP-1, в приложении)

- **Лист «Спросить историю»** — существующий, дорабатывается: выбор адресата
  (чипы: «сама бабушка», участники дерева, «ссылкой»), темы из библиотеки
  Phase D §3.3.1 (в MVP-1 — нынешние 8 вопросов + «свой вопрос», библиотека
  100+ подключается в MVP-3), кнопка «Отправить». Системный «Поделиться»
  остаётся второй кнопкой до выхода MVP-2.
- **Экран ответа** — новый, voice-first, один на пользователя и гостя
  (в вебе — та же Flutter-страница по публичному маршруту). Крупные
  цели ≥56dp, запись по одному тапу, счётчик времени, «Стоп», прослушать,
  перезаписать, «Сохранить». Текстовый режим — обычное поле; фото —
  существующий пикер.
- **Раздел «Истории» на странице персоны** — ответы как блоки статьи
  (аудио-плеер + расшифровка) с подписью источника; для инициатора —
  строка статуса своих открытых вопросов («ждём ответа», «ответила 13.09»).
- **Уведомления** — четыре типа в существующем экране уведомлений, с
  действием «Ответить» на входящем.

## 3. Бэкенд-контракт

Сущность `StoryRequest` (новая коллекция `storyRequests` в блобе; объём —
десятки записей с истечением, в таблицу выносить незачем):

```
id, treeId, personId (герой), requesterUserId,
targetUserId | null, guestToken | null (ровно одно из двух),
question {text, themeKey | null, sourceQuestionId | null},
status: pending | answered | declined | expired | revoked,
answer: {articleBlockId, kind: audio|video|text|photo, answeredByUserId | guestName} | null,
createdAt, expiresAt (30 дней — пожилым нужен запас, у kinship 14), respondedAt
```

Маршруты — зеркало `kinship-checks-routes.js`:

- `POST /v1/story-requests` — `{treeId, personId, targetUserId?, question}`;
  доступ `requireTreeAccess`; 409 на дубль открытого вопроса той же паре;
  429 на спам (порог как у kinship).
- `GET /v1/me/story-requests/received|issued?status=` — списки.
- `POST /v1/story-requests/:id/answer` — `{kind, mediaUrl?, durationSec?,
  transcript?, text?}` → `appendArticleBlock` в статью героя от имени
  адресата (право — как у редактирования персоны; для «сама бабушка» это её
  персона), запрос → `answered`, уведомление инициатору.
- `POST /v1/story-requests/:id/decline`, `POST /v1/story-requests/:id/revoke`.
- Гость: `POST /v1/story-requests/:id/share-link` → `guestToken` (одноразовый,
  30 дней); `GET /v1/public/story-requests/:token` → `{question, heroFirstName,
  requesterFirstName}` и ничего больше; `POST /v1/public/story-requests/:token/answer`
  с ограничениями: только с согласием (`consentDocVersion`), лимит 64 МБ и
  15 минут, один ответ на токен, rate-limit по IP. Ответ гостя ложится блоком
  с автором = инициатор и подписью `guestName` («рассказала Лидия, по ссылке»).
- Уведомления: `story_request_received`, `story_request_answered`,
  `story_request_declined`, `story_request_expired` — через
  `createAndDispatchNotification`, пуш с действием «Ответить».
- Блок статьи получает поле `sourceRequestId` (аддитивно), чтобы раздел
  «Истории» умел подписать «на вопрос Артёма» и не потерять связь при
  редактировании расшифровки.

**Реализовано в MVP-1 (13.09.2026, агент A) — отличия от черновика выше.**
Источник истины теперь — [STORY-REQUEST-MVP1-BRIEF.md](STORY-REQUEST-MVP1-BRIEF.md)
§0/§1 (решения Артёма зафиксированы ПОСЛЕ этого черновика); он и есть
актуальный контракт, ниже — только диф с этим документом:

- `targetUserId` **обязателен**, `guestToken` в MVP-1 не существует —
  гостевая ссылка (§3 выше, «Гость: …») целиком в MVP-2, ничего из неё не
  реализовано (нет `share-link`/`/v1/public/story-requests/*`).
- `answer.kind` ∈ `audio | text | photo` — `video` не в MVP-1 (у блока
  статьи нет типа `video`, поле `transcript` у audio-блока всегда `null`,
  §0.3/§0.4).
- Списки — ОДИН маршрут `GET /v1/me/story-requests?role=received|issued&status=`
  (query-параметр), а не два отдельных path-маршрута
  `/me/story-requests/received|issued`.
- Поле на блоке статьи называется **`source`** (объект
  `{requestId, question, askedByUserId, askedAt}`, живёт рядом с `content`),
  а не `sourceRequestId`.
- Пятый тип уведомления, `story_request_revoked` (адресату при отзыве
  инициатором), реализован — список выше был неполным.
- Доступ на создание — не общий `requireTreeAccess`, а `requireGraphPersonEdit`
  на персону-героя (инициатор обязан иметь право её редактировать); адресат
  отвечает БЕЗ своего edit-гранта — сам pending-запрос и есть разовое
  разрешение записать один блок.
- Истечение — лениво при чтении (как у kinship) плюс сметание `expired`
  старше 90 дней джобом hard-delete (`_sweepUnboundedLogs`, новый ключ).

## 4. Клиент

- `lib/backend/interfaces/story_request_capable_family_tree_service.dart`:
  `createStoryRequest`, `listStoryRequests({received|issued})`,
  `answerStoryRequest`, `declineStoryRequest`, `revokeStoryRequest`,
  `createStoryRequestShareLink`. Реализация в `CustomApiFamilyTreeService`
  по образцу kinship; UI показывает кнопку только если `service is …`.
- Экран ответа переиспользует `AudioRecordSheet` и `KruzhokRecorderScreen`;
  расшифровка в MVP-1 не обязательна (поле есть, STT — MVP-3 по Q1 Phase D).
- Публичный веб-маршрут `/story/:token` — отдельная лёгкая страница без
  shell-навигации, консент-чекбокс по существующему `consentDocVersion`.
- Копирайт: тексты вопросов уже продуктового качества
  (`family_story_question.dart`); новые строки — в том же тоне, без
  канцелярита, обращение на «ты» к родному.

## 5. Поставки

| этап | что | объём |
|---|---|---|
| **MVP-1** | сущность + маршруты + уведомления + capability-интерфейс + экран ответа + раздел «Истории» + замена share-заглушки; тесты бэкенда по образцу kinship; OTA | одна волна агентов: бэкенд, клиент; ревью и OTA — за мной |
| **MVP-2** | гостевая ссылка: токен, публичные маршруты, веб-страница ответа, согласие, мягкий invite после ответа | вторая волна; здесь же деплой веба |
| **MVP-3** | библиотека 100+ вопросов и подсказки (`/v1/me/prompts/suggested`), тизер в ленте, STT-гибрид, TTS-озвучка вопроса для пожилых | по мере отклика |

Вирусный крючок появляется в MVP-2; MVP-1 нужен, чтобы цикл «просьба →
ответ → страница» заработал внутри семьи и его можно было показать.

## 6. Решения для Артёма

1. **Гость отвечает без аккаунта** (рекомендую: галочка согласия и имя
   вместо регистрации — для 70+ регистрация убьёт конверсию) или сначала
   лёгкая учётка?
2. **Кому можно задавать вопрос**: только участникам своего дерева и гостям
   по ссылке (рекомендую), или любому пользователю по email?
3. **Срок ожидания ответа** 30 дней и напоминание на 7-й день (рекомендую)
   или без напоминаний?
4. **STT в MVP-1**: без расшифровки, только голос (рекомендую, быстрее в
   прод), либо сразу гибрид on-device → облако из Phase D Q1?
5. **Тизер в ленте**: по кнопке инициатора (рекомендую) или автоматически?
6. Q2–Q6 Phase D (курирование библиотеки, частота напоминаний, бюджет
   аудио, геймификация, тема «Война») — остаются открытыми, на MVP-1 не
   влияют.

## 7. Не делать

- Не хранить ответы в Stories: они истекают через 24 часа, а память — навсегда.
- Не класть полный ответ в Post: у поста нет аудио/видео, он только тизер.
- Не строить в MVP-1 библиотеку 100+ вопросов с движком подсказок — 8
  вопросов и «свой вопрос» достаточно, чтобы проверить цикл.
- Не переиспользовать `/invite/{token}` для гостя: он ведёт во вступление в
  семью, а не к одному вопросу.
